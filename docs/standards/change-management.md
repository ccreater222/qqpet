# 变更管理

> 结论：qqpet 的变更只分两级。重大变更必须先写草稿、经人类批准后落为 `docs/specs/`，再走“失败测试 → 实现 → 独立验证 → 合并批准”；小变更可直接实现，但仍要过受影响的质量门禁与合并门禁。人类只保留规格、不可逆操作、合并三个门禁。

## 1. 适用范围

- 适用于本仓库内所有 agent 与人类协作者的代码、配置、文档、脚本、CI 与数据操作。
- 与 `AGENTS.md` 冲突时以 `AGENTS.md` 为准；本文件负责把“怎么分级、按什么顺序做、谁批准”写清楚。
- 测试的设计、编写、运行与迭代由测试 agent 全权负责，不占用人类门禁；人类只评审需求、规格、权衡和最终合并。

## 2. 变更分级

| 级别 | 判定标准 | 典型例子 |
|---|---|---|
| 重大 | 改变跨端契约、持久化格式、权威来源、安全边界、发布/回滚路径，或需要数据迁移与不可逆操作 | WebSocket 协议字段或版本号；存档 schema / `SAVE_SCHEMA_VERSION`；device token / 配对流程；authority epoch / restore generation；preload 暴露的 `window.qqpet` 接口；Android/iOS/Harmony 原生桥方法；SQLite 表结构或迁移；Docker/Compose 的 secret 与端口模型；CI 质量门禁规则 |
| 小 | 不改变上述契约，只影响局部实现、文案、样式、测试或文档 | 局部 UI 调整与文案；不改变协议的错误提示；补充测试与夹具；文档修订与索引维护；不改变输入输出边界的重构 |

判断不清时按重大处理：先写规格草稿，由人类决定是否降级。不得为了跳过流程把重大变更拆成多个“小变更”。

## 3. 重大变更流程

1. **草稿**：在 `tmp/specs/<主题>.md` 写清目标、非目标、现状、契约/不变量、迁移、验收标准、回滚方案。草稿不进入 `docs/`，不要求符合 living docs 格式。
2. **规格批准（人类门禁 1）**：人类批准草稿的范围与验收标准；未批准前只做调查、原型和测试设计，不写生产实现。
3. **落为规范**：批准后以稳定文件名写入 `docs/specs/<主题>.md`，并更新 `docs/README.md` 与 `docs/doc-map.json`（如有新代码域）。
4. **测试先行**：先写失败测试，运行并记录命令、退出码与失败断言；红灯原因必须与预期一致（例如行为缺失，而不是语法错误或环境问题）。不得先写实现再补测试。
5. **实现**：最小可逆改动；每完成一块就运行目标测试。跨端契约要同时覆盖服务端、客户端与共享层；数据库/协议变更要写迁移或兼容策略。
6. **独立验证**：由未参与实现的 agent 按 `docs/standards/agent-change-review.md` 复核 diff、运行门禁、检查否定路径与文档同步；作者自测不能替代独立验证。
7. **合并批准（人类门禁 3）**：合并门禁通过后才可合入 `main` 或发布分支，并在交付报告中附命令、退出码、证据路径与遗留风险。

被拒绝或范围变化时回到步骤 1/2，不带着未批准的规格继续实现。

## 4. 人类三个门禁与 agent 职责

| 决策 | 谁负责 | 说明 |
|---|---|---|
| 规格批准 | 人类 | 只决定“做什么、边界在哪、验收是什么”；不审 routine 测试实现细节 |
| 不可逆操作 | 人类 | 见 §6；未批准一律停在操作前 |
| 合并批准 | 人类 | 合入 `main`、发布分支或受保护分支前批准 |
| 测试设计/红灯/转绿 | 测试 agent | 全权负责，不等待人类逐条审测试 |
| 实现细节、错误处理、重构 | 实现 agent | 在批准范围内自主决定 |
| 文档草稿与同提交更新 | 实现/文档 agent | 按 `docs/standards/documentation.md` 执行 |
| 独立验证 | 未参与实现的 agent | 重大变更必须；小变更由审查者抽查 |

“人类只有三个门禁”不等于降低质量：测试、独立验证、质量门禁和文档检查仍然必须完成，只是不需要人类逐项签字。

## 5. 小变更流程

1. 确认不改变跨端契约、存储格式、安全边界与构建/部署路径；否则升级为重大变更。
2. 直接实现，补充或更新覆盖该行为的测试；受影响的兼容测试必须通过。
3. 若命中 `docs/doc-map.json` 的 `require` 规则，同提交更新目标文档；只命中 `warn` 也应在交付说明中解释为何无需更新。
4. 运行受影响的质量门禁（至少 `typecheck`、`test:compat`、`check:docs`/`check:docs:staged`，按范围追加构建或服务端测试）。
5. 合并仍需人类批准；合并前完成 diff 自审与必要的独立抽查。

## 6. 不可逆操作清单

以下操作必须先获得人类批准，并说明影响范围、备份/回滚方式、验证方式：

- `git push --force`、删除远程分支、用 `reset --hard` 覆盖他人提交、rebase 已共享分支。
- 发布 tag、GitHub Release、上传安装包、修改发布渠道或签名材料。
- 恢复/覆盖生产或共享数据库、删除备份、修改 restore generation、执行 `--accept-rollback`。
- 轮换 owner 凭据、设备 token、TLS 私钥、CI Secrets，或把凭据写入任何持久位置。
- 部署生产服务、改变公网暴露面、修改 TLS/反代/防火墙配置。
- 批量删除资源、迁移目录、改写历史记录。

本地一次性验证、临时数据库、`tmp/` 下的可丢弃文件不属于不可逆操作，但不得触碰真实用户数据。

## 7. 测试与证据要求

- 红灯证据：命令、退出码、失败断言或错误类型；证明“因为功能不存在而失败”，不是环境坏了。
- 绿灯证据：同一命令通过；涉及并发、重连、幂等、越界、未授权的场景要有否定性测试。
- 服务端变更：`npm --prefix server run typecheck`、`npm --prefix server test`；涉及部署/镜像时追加 `npm run smoke:compose` 与 `npm run smoke:docker`。
- 客户端/共享层变更：`npm run typecheck`、`npm run test:compat`；影响启动、IPC、同步时追加 `npm run test:e2e`。
- 文档变更：`npm run test:docs`、`npm run check:docs`、`npm run check:docs:staged`。
- 验收证据写 `.agent-reports/acceptance/`；临时输出写 `tmp/reports/`；不得写入或修改 `docs/reviews/**`。

## 8. 失败、回滚与阻塞

- 测试失败先定位根因；不得改测试断言、放宽校验、加静默兜底或删除失败用例来“转绿”。
- 实现导致回归时优先 `git revert` 单个提交；共享分支禁止 `reset --hard` 改写历史。
- 发现范围超出批准规格时暂停，向父 agent 或人类报告并请求重新批准；不要自行扩大范围。
- 无法继续时给出具体阻塞：阻塞条件、已尝试步骤、需要谁做什么决定；不得把未完成说成完成。
- 文档检查工具错误（退出码 `2`）按环境问题处理，不得用 `DOCS_CHECK=off` 掩盖；跳过开关只适用于“确实无需更新文档”的提交，且必须在提交信息写 `Docs-Check: off — <理由>`。

## 9. 完成定义

一个变更只有同时满足以下条件才算完成：

- 验收标准逐条有证据，失败测试先红、实现后转绿。
- 受影响的质量门禁全部通过，退出码与关键输出已记录。
- 映射文档在同一提交更新；索引、链接、doc-map 无死规则。
- 没有越界改动、无关文件、生成物、调试输出或敏感值。
- 重大变更经过独立验证；合并已获人类批准。
- 交付报告包含：分配的 tree/task ID、文件清单、命令与退出码、证据路径、与其他作者路径的差异、剩余工作。
