# 规格索引

> 结论：`docs/specs/` 只存放已经过人类批准的长期方案；草稿留在 `tmp/specs/`，未批准内容不得进入本目录。当前已批准方案为文档同步规范与客户端数据上游迁移，后续规格按同一格式追加。

## 1. 目录用途

- 记录“为什么这样做、边界是什么、如何验收”，不记录日常操作步骤（放 `docs/guides/`）或当前实现细节（放 `docs/architecture/`）。
- 一个规格一个稳定文件名，禁止 `v2`、`final`、`draft`、`副本` 等版本/临时标记。
- 规格改变跨端契约、持久化格式、权威模型或发布路径时，必须重新走批准流程；小修订可随实现提交更新，但要在交付说明中注明。

## 2. 状态约定

| 状态 | 位置 | 说明 |
|---|---|---|
| 草稿 | `tmp/specs/<主题>.md` | 未批准，不进入 `docs/`，不要求 living docs 格式 |
| 已批准 | `docs/specs/<主题>.md` | 人类批准后落盘，作为实现与验收依据 |
| 已废弃 | 删除或合并 | 不保留第二份 living 文档；历史结论进入 `docs/reviews/` 或新规格的“背景” |

## 4. 编写要求

每个规格至少包含：

1. 背景与问题：当前事实、痛点、为什么不继续现状。
2. 目标与非目标：可验收的目标，以及明确不做什么。
3. 目录/数据/接口契约：涉及路径、字段、命令、协议或权限的变化。
4. 迁移方案：旧数据/旧路径/旧调用方如何过渡，失败如何回滚。
5. 验收标准：可执行命令、预期退出码、证据位置。
6. 风险与回滚：最坏情况、检测方式、恢复步骤。

规格中引用其他文档时使用相对链接；引用历史证据只链到 `docs/reviews/README.md` 或对应目录说明，不复制报告正文。
